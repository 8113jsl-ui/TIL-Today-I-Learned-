# CRUD와 HTTP 메서드 정리

학습일: 2026-08-27

수업에서 CRUD와 GET, POST, PUT, PATCH, DELETE를 배웠다. 필기를 복습하면서 데이터에 하는 작업과 HTTP 요청의 의미를 구분해 정리했다.

## CRUD는 데이터에 하는 네 가지 작업이다

CRUD는 생성(Create), 조회(Read), 수정(Update), 삭제(Delete)를 뜻한다. HTTP 메서드는 클라이언트가 서버에 어떤 처리를 요청하는지 나타낸다. 둘은 서로 연결해서 설계할 수 있지만, 완전히 같은 개념은 아니다.

할 일 API를 만든다고 가정하면 다음처럼 정리할 수 있다. 아래 주소와 데이터는 복습용 예시다.

| 작업 | 요청 예시 | 의도 |
| --- | --- | --- |
| 생성 | `POST /todos` | 새 할 일 생성 |
| 조회 | `GET /todos/1` | 1번 할 일 조회 |
| 전체 교체 | `PUT /todos/1` | 1번 할 일의 표현 전체 교체 |
| 부분 수정 | `PATCH /todos/1` | 완료 여부 등 일부 항목 수정 |
| 삭제 | `DELETE /todos/1` | 1번 할 일 삭제 |

POST는 생성에 자주 쓰지만, 생성만을 위한 메서드는 아니다. 서버에 데이터를 제출해 처리를 요청할 때도 사용한다. PUT은 대상이 없을 때 생성하는 용도로도 사용할 수 있으므로, 구체적인 동작은 API 문서를 확인해야 한다.

## PUT과 PATCH의 차이

할 일이 다음과 같다고 가정한다.

```json
{"title": "HTTP 복습", "completed": false}
```

PUT으로 전체 교체를 요청한다면 제목과 완료 여부를 포함한 전체 표현을 보낸다. PATCH는 `{"completed": true}`처럼 일부 항목을 바꾸는 요청을 설계할 때 사용할 수 있다. 다만 PATCH의 본문 형식과 적용 규칙은 API에서 정한 규약을 따라야 한다.

필기에 적은 'PUT이 잘 안 되면 POST로 바꾸기'는 일반적인 해결책으로 삼기 어렵다. 서버가 해당 메서드를 허용하는지, 경로와 본문 형식이 맞는지 먼저 확인해야 한다.

## 같은 요청을 반복했을 때도 생각하기

멱등성은 동일한 요청을 여러 번 보내도 서버에 의도한 효과가 한 번 보낸 것과 같은 성질이다. 응답 코드나 응답 내용이 매번 같아야 한다는 뜻은 아니다.

- GET은 조회용이며 안전하고 멱등적이다. 조회 요청으로 데이터를 삭제하도록 설계하면 안 된다.
- PUT과 DELETE는 멱등적이다. 같은 자원을 다시 삭제했을 때 응답이 달라도 삭제된 상태는 유지된다.
- POST와 PATCH는 멱등성이 보장되지 않는다. 특히 같은 생성 요청을 재전송하면 항목이 중복으로 생길 수 있다.

PATCH도 값을 특정 상태로 설정하는 등 멱등적으로 설계할 수 있다. 하지만 메서드 이름만 보고 모든 PATCH 요청이 멱등적이라고 가정하면 안 된다.

## 매개변수와 메서드는 별개의 요소다

`GET /todos?completed=true`에서 GET은 메서드, `/todos`는 경로, `completed=true`는 쿼리 매개변수다. 매개변수를 사용하는 것과 HTTP 메서드를 구분하는 것은 양자택일이 아니다.

오늘 복습의 핵심은 메서드 이름을 CRUD에 대입해 외우는 데서 끝내지 않고, 전체 교체인지 부분 수정인지, 재전송하면 어떤 효과가 생기는지까지 생각하는 것이다.
